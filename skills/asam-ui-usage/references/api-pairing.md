# 固定包与 API/SFC 配对

接入前分别固定产品包、Skill 和网站资料的来源。相同版本号不保证候选字节相同，网站源码提交也不等于产品包提交或 npm 发布版本。

| 输入                       | 核对内容                                                                              | 能证明的范围                                      |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 核心、图标、adapter 产品包 | 各自生产提交、tarball SHA256、package.json、exports、声明与入口哈希、peerDependencies | 本批真实交付接口与依赖；包分别核对                |
| Skill 分发包与安装器       | Skill 提交、归档 SHA256、外部来源清单、归档内 manifest 文件哈希                       | 安装的具体 Skill 字节；不表示其快照与当前产品相同 |
| 网站 API 聚合              | 实际 sourceSha 或构建来源字段、公开根入口、相关声明/sourceHash、继承和关联链接        | 此次生成所依据的声明；不能用旧聚合代替新候选      |
| 原生 SFC 示例              | 对应公开入口、demo、TS/JS 变体、manifest、逐文件 SHA256、运行入口                     | 面板源码与运行示例来自相同文件；变体分别核对      |

先读实际安装包与 Skill 的 `references/package-contract.json`，按文件哈希比较；快照较旧时重新读取安装包，记录差异。`runtime.components` 只描述组件三条导入路径；服务、指令、全局属性与别名单独核对，不能按总数填充 resolver 支持表。

再配对同次网站构建的 API、示例与内容清单。存在 `sourceSha` 时比较它们是否相同，同时核对相关产品来源与文件哈希；组件索引可能使用 `docsVersion` 等来源字段，缺少 `sourceSha` 不补造值。仅有有限 API audit、单个组件或旧版聚合时，记录其真实入口和覆盖范围，不把它升格为整库 API/SFC 一致结论。

公开类型中的联合、调用签名、索引访问、继承来源和默认值应保留原含义。未知默认值不能猜测；明确 `undefined` 的默认值不改成文档建议值。元数据中的依赖声明路径是溯源信息，不一定是消费者可打开的公网链接，使用交付方实际公开的类型入口与资料地址。

网站资料缺少或不同源时，可以按已安装包完成有证据的接入，并列出尚待配对的资料；不使用缺失的示例或计划接口，也不维护第二份 props 表。交付分别记录类型检查、构建、注册、服务/指令交互、尺寸视觉、独立 QA/ACC 的结果；源码确认与历史有限验收不能互相替代。
