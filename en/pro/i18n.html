Unified language and internationalization ​

UI and Pro use one scope for their own default messages and native component locales. Host titles, slots, render functions, business fields, user input, and original server messages retain their values. The host application chooses its business translation framework.

Choose a version and matching packages ​

Use case Matching packages Entry point
1.0 base components and Yudao adapter UI 1.0.0. Pair the adapter with UI Yudao 1.0.0 when you use it. @asam-ui/ui/i18n and the existing AsamConfigProvider
2.0 base components UI 2.0.0-rc.1 The same UI entry point. Pro is optional.
2.0 UI and Pro UI and Pro at the matching 2.0.0-rc.1 version @asam-ui/pro/i18n, sharing the UI context

The complete project ZIPs include the matching packages, integrity lockfile, and required type patches. Extract a ZIP and run pnpm install --frozen-lockfile, pnpm run typecheck, pnpm run dev, and pnpm run build. Use the bundled archives for these entry points. Archive names and version numbers can also appear on older builds. Regenerate the lockfile if you replace the vendor archives. Use the UI entry point alone in a 1.0 project.

Quick start for 1.0 and UI-only 2.0 ​

vue
<template>
	<AsamConfigProvider :i18n="scope">
		<AsamButton @click="language = language === 'zh-CN' ? 'en' : 'zh-CN'">
			中文 / English
		</AsamButton>
		<AsamFormActions />
	</AsamConfigProvider>
</template>
<script setup lang="ts">
import { onScopeDispose, ref } from 'vue';
import { AsamButton, AsamConfigProvider, AsamFormActions } from '@asam-ui/ui';
import { createAsamI18n } from '@asam-ui/ui/i18n';
const language = ref<'zh-CN' | 'en'>('zh-CN');
const scope = createAsamI18n(() => ({ locale: language.value }));
onScopeDispose(scope.dispose);
</script>

The standalone 1.0 project and the 2.0 base component project each lock their own UI package. Keep the existing provider for Yudao data adapters. The host remains responsible for business dictionaries, permissions, and APIs.

The 1.0 language API and types come from the public declarations in UI 1.0.0. The 2.0 language API and types come from the matching UI and Pro declarations.

Integration and ownership ​

Create a scope in Vue setup and pass that instance to the existing provider. Use the host's reactive input as the source of the locale.

vue
<template>
	<AsamApplicationProvider :config="{ base: { i18n: scope } }">
		<AsamFormActions />
		<AsamStatePanel :title="scope.t('pro.common.empty')" />
	</AsamApplicationProvider>
</template>
<script setup lang="ts">
import { onScopeDispose, ref } from 'vue';
import { AsamFormActions } from '@asam-ui/ui';
import { AsamApplicationProvider, AsamStatePanel } from '@asam-ui/pro/components';
import { createAsamProI18n } from '@asam-ui/pro/i18n';
const language = ref<'zh-CN' | 'en'>('zh-CN');
const scope = createAsamProI18n(() => ({ locale: language.value }));
onScopeDispose(scope.dispose);
</script>

For UI alone, use AsamConfigProvider and createAsamI18n from @asam-ui/ui/i18n. Give each Vue root and each SSR request its own instance. Its owner calls dispose. Keep mutable locale state out of module singletons. Ordinary factories accept an explicit scope, and components use useAsamProI18n. Without the unified entry point, scope.enabled.value is false and the previous defaults apply.

The unified entry point defaults to zh-CN, accepts the alias zh-cn, and uses en for English. Register other identifiers such as en-US explicitly. Existing complete Element Plus locale objects keep their original precedence. Regional formatting applies when the caller omits locale. Explicit formatting takes precedence, and DTOs, currencies, time zones, and parsing follow their existing rules.

Responsibility Integration Host values and precedence
Component messages The scope resolves ui.*, pro.*, and library-owned app.* messages. Props, slots, render functions, and explicit empty strings keep their existing precedence.
Business translation Use the existing business framework or the demonstration host's dictionary. Menus, schema labels, business data, user input, and original server messages belong to the host.
Language preference Use the existing preferences owner, storage, restore, and choose. Components read the preference. The host owns storage and browser-language detection.
Regional formatting Use the public locale and format parameters. An enabled scope supplies the default locale. DTOs, currencies, time zones, parsing, and serialization follow the existing application rules.

A language change updates presentation while preserving field schemas, drafts, and selections. Existing requests, saves, validation, and verification of uncertain outcomes keep their previous execution state. To update how a previously recorded error appears, call the formatter in reactive rendering and leave the diagnostic record intact.

Resources, overrides, and additional languages ​

Complete built-in resources ​

Message resources Simplified Chinese English
UI (matching 1.0 or 2.0 package) @asam-ui/ui/i18n/zh-CN exports asamMessagesZhCn @asam-ui/ui/i18n/en exports asamMessagesEn
Pro (2.0) @asam-ui/pro/i18n/zh-CN exports asamProMessagesZhCn @asam-ui/pro/i18n/en exports asamProMessagesEn

The complete built-in languages are zh-CN and en. The zh-cn alias preserves compatibility. The host explicitly maps or registers identifiers such as en-US, en-GB, and French. Element Plus and Day.js maintain their own language lists. Existing calls using the asamLocaleEn and asamLocaleZhCn locale objects still work. The new message resources use flat keys.

Use the messages option in createAsamProI18n for small overrides. The standalone exports asamProMessagesEn and asamProMessagesZhCn come from @asam-ui/pro/i18n/en and @asam-ui/pro/i18n/zh-CN, respectively. Use AsamProMessages to check the resource type. Each language entry point is independent of the other language and the component runtime. Specify from when auto-importing resources that share a name.

ts
const scope = createAsamProI18n({
	locale: 'en',
	messages: { en: { 'pro.common.empty': 'Nothing here yet' } }
});

For dynamic keys and parameters, use the correlated AsamI18nCall tuple or narrow the type in a branch. Messages use plain-text placeholders such as {name} and escape braces by doubling them. For English plurals, use plural with forms and the required other form. Intl.PluralRules uses the locale of the selected resource. The output is plain text.

Explicit props, slots, and render functions retain their existing precedence. The scope looks up messages in the current effective language, then the explicit fallbackLocale, then zh-CN. Within each language, host overrides precede registered resources and package defaults. If the message is missing throughout the chain, the scope reports missing-message and returns an empty string.

Register an additional language by providing both messages and the native locale mapping, for example languages: { fr: { messages, nativeLocale } }. If a date control needs a Day.js language module, the host imports the public module and keeps the language scoped to the application. Partial messages or a native locale cover only what they define. For asynchronous loading, the host calls load, register, and choose explicitly. Switch after resources are ready, retain the previous language on failure, and keep the newest choice if an older load finishes late. Downloading language resources is the host's responsibility.

For existing preferences, createPreferencesI18n, bindPreferencesI18n, and createLocaleLoader are available from @asam-ui/pro/application/preferences. Business dictionaries, storage, and restore behavior follow the existing preferences contract. With Vue I18n or a similar framework, read its locale ref and continue routing business messages through its t function. Applications without such a framework can use the component scope directly.

For example, createAsamProI18n(() => ({ locale: composer.locale.value })) reads a host framework's locale ref. If the host uses en-US, map it to en or register it explicitly. Keep business titles in composer.t. The complete example illustrates this boundary with a small host dictionary.

Migrate existing usage ​

  1. Keep the existing provider, component interfaces, and explicit native locale. Create a scope under the existing application owner, then pass it through i18n or config.base.i18n.
  2. Replace only the defaults owned by the library or template. Let business labels, ordinary errors, and server messages keep their existing translation or display path.
  3. Use bindPreferencesI18n with an existing owner. Use createPreferencesI18n for a new owner. Move copied templates' compatibility imports to @asam-ui/pro/application/preferences to consume the shared translation implementation.
  4. Specify the import source for each language entry point. Manual imports, auto-imports, and existing global registration can coexist. Pass the scope to the provider to supply the active language.
  5. Verify that existing errors, drafts, filters, selections, focus, and pending state survive language changes before enabling the integration in a business application. The examples leave validation, saves, and requests in their existing state.

Template-local defaults ​

A template carries its own app.templates.<name>.* resources and parameter declarations. Call useAsamProI18n(localDefaults) in setup to get an inherited scope. Pass it to the subtree through AsamConfigProvider.i18n or AsamApplicationProvider's config.base.i18n. Host overrides take precedence over local defaults. Local defaults inherit the current locale, and the owner releases the local binding when it exits.

Existing errors and native validation rules ​

createAsamMessageIssue and createAsamMessageError explicitly bind a typed key and parameters. Plain strings stay plain. An existing Error keeps its identity, message, cause, and error type. Parameters are captured as a snapshot. Private message provenance is excluded from enumeration and JSON.

ts
import {
	createAsamMessageIssue,
	createAsamMessageRuleMessage,
	formatFieldIssue
} from '@asam-ui/pro/i18n';
const issue = createAsamMessageIssue('Name is required', 'ui.form.required', { label: 'Name' });
const rule = { required: true, message: createAsamMessageRuleMessage(issue) };
// The native engine determines when a rule fails. Reactive rendering formats the existing issue.
const display = () => formatFieldIssue(issue, scope);

Use fieldLabels to supply display labels keyed by field.key. In CRUD, queryFieldLabels sets query labels independently. A missing entry falls back to the original label, while an explicit empty string stays empty. Display mappings leave the schema and reset watchers unchanged. Host rules, server feedback, and audit history keep their original text.

API and public types ​

Entry point Contract
createAsamProI18n(options?, parent?) Creates a scope for an application, code outside components, or SSR. Reuses the UI implementation. The owner calls dispose.
useAsamProI18n(defaultMessages?) Reads the nearest UI scope in setup, optionally adds local defaults, and releases the binding with the owner.
formatFieldError(value, scope?, formatExternal?, display?) Displays a recorded error. Resolves only explicitly attributed messages and supports a separate display context.
formatFieldIssue(issue, scope?, display?) Displays a recorded issue while keeping its original message and cause.
createAsamMessageIssue(legacy, ...call) Creates an issue with message provenance. call uses the same correlated parameter tuple as scope.t.
createAsamMessageError(legacyOrError, ...call) Explicitly binds message provenance to a new or existing Error.
createAsamMessageRuleMessage(issue) Returns the native rule message function. Switching languages leaves rule execution and callback counts unchanged.
asamProMessagesEn / asamProMessagesZhCn Complete resources from the two language entry points. The aggregate entry point also exports them.

Import these functions and the AsamProMessages, AsamProMessageParameters, and AsamFieldMessageDisplayContext types from @asam-ui/pro/i18n. Import the scope, options, and message-call types AsamI18n, AsamI18nOptions, and AsamI18nCall from @asam-ui/ui/i18n. The same entry point exports AsamI18nKey, the Vue injection key for the scope. The existing compatibility exports from the Pro package root remain available.

Language, regional formatting, and native behavior ​

Area Current support
Languages Complete built-in Simplified Chinese and English. Register additional resources explicitly and choose a fallback for missing entries in partial resources.
RTL Complete RTL layout, directional mirroring, icons, and native control adaptation require separate support. Arabic or Hebrew message registration covers the supplied text.
Regional formatting The host supplies region, currency, and time zone. Explicit format parameters take precedence, and Intl support depends on the target runtime. Models, parsing, and serialization retain their existing behavior.
Element Plus Uses the public locale. Complete existing locale objects retain their priority, and native controls keep their blank-title fallback, other behavior, and compatibility limits.
Date controls The host imports any required public Day.js language modules and keeps application language scoped. Verify date controls, input methods, and browsers in the host.
Native notifications Strings submitted to imperative APIs are snapshots. To follow language changes, keep the object with its message provenance and read it during reactive rendering.
SSR Create and dispose a separate scope for every request. The core SSR example covers that lifecycle. Verify hydration, native controls, and regional formatting in the host.

Page buttons, example titles, and business dictionaries belong to the example host. The matching packages provide library-owned defaults. Verify keyboard behavior, focus, layout, and native control compatibility in the target application.
